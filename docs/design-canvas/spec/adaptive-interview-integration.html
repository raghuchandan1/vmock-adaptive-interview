1 · Summary

What we are adding

A practice interview that reads the student's CV and optional job description, then asks follow-up questions based on what they actually answer. Today's Studio interviews play a fixed list of questions. The adaptive interview has a hidden plan, decides each next question during the session, and ends with written, qualitative feedback.

Where it lives
Studio Conversations, as a new option in the existing Generate Interview wizard (mode=adaptive). The Home “Interview” card and the Interview & Offer → Interview Practice step already lead there, so they stay unchanged.
Inputs
The student's saved CV and a job description (saved one, pasted text or PDF), reusing the wizard's existing pickers. The service receives plain text only: resume_text and jd_text.
Interview
Voice, video or typed, all feeding the same text answer. The video and delivery analysis already in VMock keep working. This design covers the content of the conversation.
Feedback
Inside the existing feedback page. Non Verbal and Delivery of Speech are unchanged. Content Strength keeps VMock’s question-type rubric, so the Level is calculated as today. The adaptive feedback adds where each rubric element appeared (✓ first answer, ↩ added when the interviewer asked, ✕ still missing), the follow-ups, quotes, and how to answer next time.
Out of scope
The non-verbal, speech, Word Usage & Tone and Level calculations (existing pipeline, run per question segment). Speech-to-text.

Assumptions to confirm

  • Assumption VMock supplies parsed CV text to the service (the wizard's CV picker already has it).
  • Assumption Voice and video are transcribed by VMock's existing pipeline; the service only receives final text per answer.
  • Assumption VMock maps the engine’s rubric elements (situation, result, depth…) to its own Content Strength chip names.
  • Assumption Route is the existing wizard with a mode parameter, not a new product area.

Findings that shaped the design

  • The service requires a CV of 200+ characters. So “Job description only” is hidden in adaptive mode.
  • With no JD, a target role is required. The setup step asks for it only then.
  • The question list must stay hidden. The live screen cannot show the usual “Interview Questions” list.
  • Planning is one blocking call; there are no progress events to stream.

5 · Integration

How the pieces fit

The prototype is a zero-dependency Node service. Developers can keep it as a separate service, or lift lib/engine.js, lib/schemas.js and prompts/ into the VMock backend.

flowchart LR
  W[VMock web app
wizard, live screen, feedback] -->|session auth| B[VMock backend
CV text, JD text, user id]
  B -->|server to server| S[Adaptive interview service
routes + engine]
  S --> P[(Session store)]
  S -->|planner once
turn per answer
feedback once
grounding per rewrite| L[LLM provider]
  W -. video, audio .-> V[Existing recording and speech pipeline]
  V -. final transcript text .-> W

Four model calls, one rule engine

  • Planner (prompts/planner.md): once. CV and JD to claims, competencies, concerns and a slot plan.
  • Turn (prompts/turn.md): per answer. Proposes the next move.
  • Engine (lib/engine.js): code, not model. Follow-up budgets by style (1 / 2 / 3, +1 on claim topics), pivots, time rule, “not sure” rules, wording guards. A disallowed decision is rejected and re-requested.
  • Feedback (prompts/feedback.md): once after the end, then a grounding call per rewrite.

Student never sees the plan

  • publicView returns only id, status, pre_brief, transcript.
  • The full session (plan, raw model inputs and outputs, latency, tokens) exists only at the trace endpoint. Keep it staff-only.
  • CV, JD and answers are untrusted text. Every prompt says never to follow instructions found in them.
  • Feedback strips scores and agenda words, keeps only verbatim quotes from the same topic, and drops rewrites with invented numbers.

Limits baked into the code

Scored topicsshort 3 · standard 4 (plus warm-up and closing)
Interviewer turn capshort 16 · standard 20
Planned timeshort 10 min · standard 15 min
Input sizeCV or JD up to 30,000 characters · answer up to 20,000 · request body up to 2 MB
Model call3 attempts, 150 s timeout each. Reasoning effort is dropped on retry if the model rejects it.
DefaultsTurn model gpt-5-mini, effort low. Planner effort medium. Override with PLANNER_MODEL, PLANNER_REASONING_EFFORT, TURN_MODEL, TURN_REASONING_EFFORT, OPENAI_BASE_URL.
Feedback versionFEEDBACK_VERSION = 9. Cached feedback with an older version is regenerated.

7 · Production gaps

What the prototype does not do yet

Not safe to expose as is. These are facts about the current code, found while reading it. The test suite passes (all checks), but it covers the interview logic, not production concerns.

Security and access

  • No authentication, and no link between a session and a user. Any caller can read any session by id.
  • GET /api/sessions lists every session. GET …/trace returns the hidden plan.
  • POST /api/key lets any caller replace the model key. Remove it; read the key from server config.
  • No rate limiting on a route that makes paid model calls.

State and scaling

  • Sessions are JSON files under sessions/, cached in memory. Move to the VMock database, owned by user id.
  • The “one answer at a time” lock is an in-memory set. With more than one instance it needs a shared lock.
  • Sessions store full CV and JD text and raw model output. Confirm retention and privacy policy before storing.
  • Prompts are read from disk on every call (convenient for tuning). Cache them in production.
